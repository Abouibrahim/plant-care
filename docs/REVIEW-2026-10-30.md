# Review of 2026-10-30: enhancements and optimizations

As of 0.9.0 (commit 7b03f31). The whole repository was read: the functions under `api/`, the app under `src/`, the prompts, `supabase/schema.sql`, the tests, the docs and the phase files. The four checks pass on this checkout: typecheck, lint, 144 tests, build (main bundle 806 KB, 238 KB gzip; Leaflet 45 KB gzip in its own chunk).

Nothing below is implemented. Each item says roughly what it takes (S: an hour or two, M: half a day to a day, L: more) and whether it needs a ★ step, something only Mohamed can do: SQL in the Supabase editor, a dashboard setting, a key.

## What to leave as it is

- The reminder engine. Task identity, windows across the year end, stale and missed waterings, the snooze, the rain skip and the carried-over windows are each reasoned through in `docs/DECISIONS.md` and pinned by a test. Nothing found contradicts the documented behaviour.
- The handling of paid calls. Ids made on the phone, upserts on retry, the keep-alive on long calls, the lookup after a lost profile reply, the save-before-unmount of a diagnosis or an answer. This is more careful than most apps of this size.
- The graceful degradation before each ★ table exists, and the owner-only routes with the 401, 403 and 502 distinction.

## 1. Do first (little or no code)

### 1.2 Confirm that sign-ups are off, then stop depending on it (★ SQL, S)

The anon key ships in the app and every table policy is `to authenticated using (true)`. With "Allow new users to sign up" on (Supabase's default; the ★ check in `PHASE6.md` is unchecked), anyone who has the app's address can create an account and read or change every table and every photo. The Claude key is safe either way (`OWNER_USER_ID` on the routes); the data is not.

Proposal: an `owners` table with one row, and policies that read it. `supabase/schema.sql` stays generic (one insert after creating the user, as README step 1 already asks); the functions keep the service role and `OWNER_USER_ID`; nothing changes in the app.

```sql
create table owners (user_id uuid primary key references auth.users(id) on delete cascade);
insert into owners (user_id) values ('<the UUID under Authentication → Users>');
alter table owners enable row level security;
create policy owners_read on owners for select to authenticated using (user_id = auth.uid());
-- then, for each table, drop policy owner_all and create:
create policy owner_all on <table> for all to authenticated
  using (exists (select 1 from owners o where o.user_id = auth.uid()))
  with check (exists (select 1 from owners o where o.user_id = auth.uid()));
-- and the same expression on the "owner photos" policy of storage.objects
```

## 2. Robustness

### 2.1 A lost reply should not lose an Ask answer or a check (M)

The profile has its lookup after a dropped connection (0.8.2); Ask and Check do not, and both run a minute at medium effort on mobile data. The route can write the row itself under an id the app makes before the call: the app sends `id`, `thread_id` and `asked_at` with the question (or `id` and `checked_at` with a check), the route inserts the row with the service role once Claude answers, then replies. The app's own insert then meets the unique id (`23505`), which it already treats as saved; on a status-0 error it asks `questions` (or `planting_checks`) for that id every 10 s until the function must have stopped, as `api.profile` does. Diagnose would need the photo uploaded before the call (its path is planned already) and the route writing `photos.ai_result`: a second step.

### 2.2 Save should not wait for the expansion (S)

`CaptureScreen.save` awaits `api.expand({ plant_id })` before navigating (`src/screens/CaptureScreen.tsx:449`): on a slow connection the Save button spins through the function's cold start and its ten or so queries after the plant is already stored. Navigate once the photo rows are written and let the expansion run behind; the Plant screen's Calendar tab reads the tasks when it opens, and Today expands anyway.

### 2.3 Know when the morning run happened (S, no SQL)

Vercel documents the Hobby cron as "per-hour (±59 min)": `0 5 * * *` fires anywhere between 06:00 and 06:59 Tunis. Today's re-read is pinned to 06:05 (`MORNING_RUN_MINUTE` in `src/screens/TodayScreen.tsx`), so a list read at 06:30 before a 06:45 run keeps showing waterings the rain then skipped, until the next day or a manual refresh. And on Hobby the runtime logs reach back one hour, so a failed run is invisible by breakfast.

Proposal: `api/daily.ts` writes the `settings` key `daily:last` = `{ at, today, created, removed, expired, superseded, skipped, pushes_sent, pushes_failed, weather_error, digest_error }`. Today re-reads when that `at` is newer than its load; the Settings weather card shows "Last morning run: 06:41, 3 tasks added, 2 waterings skipped", or the error.

### 2.4 Show the doubled retry (S)

`callJson` re-sends the whole call at double `max_tokens` when the output is cut, paying both attempts; the app shows the summed tokens but not that a retry happened. Add `retries` to `Usage` so the usage line can say "(retried at 12,000)". The decision to raise a budget then rests on numbers in the app rather than on the Console.

### 2.5 Run the functions next to the database (★ check, S)

Vercel's default function region is Washington (`iad1`). If the Supabase project is in Europe (Project Settings → General → Region), every query crosses the Atlantic: Ask runs six queries, the expansion about ten, each 80 to 120 ms. Set `"regions": ["fra1"]` (or the region nearest the project) in `vercel.json`; Hobby allows one region.

### 2.6 Verify tokens without a round trip (★ dashboard, S, optional)

`verifyUser` calls `auth.getUser(token)` on every request: one GoTrue round trip before any work, and the 502 path when GoTrue blinks. With the project on asymmetric JWT signing keys (Authentication → JWT Keys), `supabase.auth.getClaims(token)` verifies the signature against the project's JWKS, which is cached, and returns `sub`; the owner check stays and an expired token still reads as 401.

## 3. Speed on the phone

### 3.1 Thumbnails written at upload (M, the biggest win)

Every list thumbnail is the full 1,280 px JPEG (250 to 400 KB): the Plants list, the map cards, the journal, the diagnoses. Fifty plants on the list is 15 MB of photo over mobile data for 48 px tiles. `prepareImage` already holds the canvas; a second `toBlob` at 320 px on the long edge (about 15 KB) stored beside the original as `<plant>/<ts>.thumb.jpg` brings that under a megabyte. `PhotoImg` takes a `size` prop and picks the thumb for tiles; a photo stored before the change falls back to the original (try the thumb, then the original; no column needed). Existing photos: a one-off "make thumbnails" button in Settings, or leave them.

### 3.2 One signing request per screen, not one per photo (S)

`photoUrl` signs each path on its own (`src/lib/db.ts:183`): the Plants list with 60 plants makes 60 requests to Storage before the first thumbnail shows, six at a time. `createSignedUrls(paths, ttl)` signs a list in one request: collect the paths asked for in the same tick (a microtask queue inside `photoUrl`) and sign them together; callers do not change. Also, `latestPhotos` sends every plant id in one `in.(...)` filter and reads whole rows (`ai_result` included) for every photo of every plant to keep the newest; a `latest_photos` view (`distinct on (plant_id)`, `with (security_invoker = true)`, ★ SQL) or at least `select("plant_id, storage_path, taken_at")` keeps that read small as the photos accumulate.

### 3.3 Keep thumbnails on the phone (S)

Signed URLs change every hour, so neither the browser cache nor the service worker keeps a photo across app starts. `PhotoImg` can fetch the signed URL itself, put the blob in the Cache API under a stable key (`/photo-cache/<path>`) and show an object URL; the next start reads the cache first and never touches Storage for a photo already seen. With 3.1 this makes the Plants list and the map readable at the farm without signal. Bound the cache (500 entries) and drop a plant's entries when it is deleted.

### 3.4 Lean reads where the profile is not shown (S)

`listPlants`, `listAllPlants` and `TagsScreen` select `species(*)`: the whole profile (calendar, pests, uses; several KB) for every plant, to show two names. A `species(id, scientific_name, cultivar, common_names)` select for the lists; `getPlant` keeps the full profile.

### 3.5 Today without the network, then Done without the network (M, then M)

The shell is precached, but Today shows a spinner until Supabase answers and an error without signal. Step one: keep the last loaded Today (tasks, done count, weather rows; a few KB) in `localStorage`, render it at once marked "as of 07:12", and replace it when the fresh read lands. Step two: queue Done, Skip and Snooze made offline (each is one idempotent update guarded by `status = pending`; the snooze is the hard one and can stay online-only) and replay them on reconnect, with the card ticking at once as it does now. The expansion and the Claude calls stay online-only.

### 3.6 A smaller main bundle (S, parse time only)

Every chunk is precached, so this is cold-start parse time, not download: 806 KB of JavaScript is roughly half a second on a mid-range phone. Three cheap cuts: lazy routes for Capture (which brings `exifr`), Species, Check and Settings, as Tags and the maps already are; `exifr/dist/lite.esm.mjs` instead of the full build (the app reads GPS and DateTimeOriginal only; check both still parse on a phone photo); drop the `.woff` from the precache (`globIgnores`), since the `.woff2` is what Android loads.

## 4. Reminders and the cron

### 4.1 The digest reads 90 days of tasks with a calendar in every row (S)

`loadDigestTasks` (`api/_push.ts:41`) reads every pending task up to today + 90 with `plant:plants(tag, site, species(care_calendar))`: the species calendar (2 to 4 KB) repeated on each row, a thousand rows in a wet summer, for a digest that uses tasks due today or exactly `lead_days` ahead. Read the calendars once (`species(id, care_calendar)`), take the largest `lead_days` across them, and read tasks up to today + that lead with `plant:plants(tag, site, species_id)`. Same message, a tenth of the bytes; `tests/digest.test.ts` adjusts.

### 4.2 The digest in French (S)

Left as a follow-up in Phase 5. The `settings` table exists now: the Language card writes `settings.lang`, `api/daily.ts` reads it and picks `fr` or `en` for `composeDigest`, `composeWeatherMessage` and the expansion notes (the French table already carries those keys).

### 4.3 Done, all the waterings at a site (S)

After a watering round the Today screen asks for one tap per tree. A "Done: all N waterings" button on a site's heading closes them in one update (`in("id", ids).eq("status", "pending")`), with one toast and one Undo that reopens the set.

### 4.4 The notification opens its site (S)

The farm digest can carry `url: "/?site=farm"`; Today reads the parameter and selects the chip, so the tap lands on the tasks the notification named.

## 5. Claude calls and cost

### 5.1 Where the money is, and what caching does here

At Fable 5.1 prices ($10 per million input tokens, $50 per million output, cache reads $0.25 per million) the output, thinking included, is about three quarters of every call: a profile about 15 cents, a check or a question 10 to 18, a diagnosis 5 to 10, an identification 5. The cached block (`prompts/system-context.md`, about 600 tokens, just above the 512-token minimum Fable caches) is written at 1.25× on most calls and read back only within five minutes, which happens inside an Ask conversation and almost nowhere else. Either way it is about a tenth of a cent per call: caching is not a lever in this app. One free change: move the `cache_control` marker to the rules block (`opts.rules` in `api/_claude.ts`), which is just as static per call, so the burst case reads 1,200 tokens instead of 600. Do not use the 1-hour TTL (a 2× write for gaps that are usually longer than an hour).

### 5.2 Try `low` effort for Ask and Check, measured (S)

Thinking is billed as output. `thinking_tokens` is already stored with every answer and check, so the experiment costs nothing to read: ten real questions at `effort: "low"`, the answers compared, the token lines compared. Fable at low effort is documented as matching earlier models at their highest; a question about watering does not need medium. Keep medium for the profile and the diagnosis, where the doubled retry already covers the long ones.

### 5.3 A usage ledger (S, no SQL)

The usage is shown per call and added up nowhere. Each route can add its usage to a `settings` row `usage:YYYY-MM` (`{ calls, input, output, cache_read, by_route }`) with the service role after the call; Settings shows "Claude this month: 23 calls, about $2.10" with the list prices in one constant. The profile call's usage, which today is shown once and lost, lands there too.

### 5.4 Prompt hygiene (S)

`prompts/system-context.md` carries a fixed list of species on site. It is already behind (the pear confirmed on 2026-10-29 is not in it) and drifts with every capture. Either shorten it to the site's character and let the inventory speak in the calls that send it (Check, Ask's neighbours), or build that line from the library at call time as a second, uncached system block. The "goats are planned" sentence lives in three prompt files; one place.

### 5.5 Two photos for a diagnosis (S)

`/api/diagnose` accepts two images and the panel sends one. A close-up and the whole plant together settle many cases; "Another photo" could add instead of replace, as Capture does.

## 6. For the grower

### 6.1 Log care done by hand (S, no SQL)

The journal only knows what the app asked for; a feed, a pruning or a mulch done unasked is not recorded, and Ask then says "the app has no record of". A "Log something done" sheet on the Plant screen writes a done task (`rule_key` `manual:<uuid>`, the type chosen, a short title, today's date, an optional note). The expansion never touches acted rows, the journal lists it, and Ask's "last time each kind of task was done" picks it up by type. Pending one-off reminders ("stake it on Friday") are the same row left pending, with `manual:` added to the carve-out beside `diagnosis:` in `api/_tasks.ts` so the obsolete-rule cleanup leaves them alone.

### 6.2 A note on Done (S)

Skip takes a reason; Done takes nothing. An optional note on Done ("12 kg", "cut back to three leaders") goes to `tasks.note`, which the journal already shows in place of the title. For harvest tasks it is a yield log for free.

### 6.3 Back everything up (S)

The two CSVs cover plants and tasks. The profiles (paid for), the diagnoses, the questions, the checks, the settings and the photo paths live only in a free-tier project with no point-in-time recovery. A "Back up everything" button writes one JSON file with every table (the paging readers exist) and the photo paths; a restore script is a later step, but a file in Downloads already turns a lost project into an afternoon instead of a loss.

### 6.4 Hand a list back to Claude (S)

Left as a follow-up in Phase 5: one hand edit pins the whole calendar or pests list for every regeneration, and the only way out is the table editor. A "Let Claude rewrite this on regeneration" action on the ListCard removes the key from `species.user_edits`.

### 6.5 Finding plants and species (S)

Species has no search; Plants filters by site and text only. A search box on Species, zone chips (from the Settings lists) and a sort (tag, zone, what is due) on Plants cost little and matter from about fifty plants on.

### 6.6 A rain gauge (★ column, M, if the model proves wrong)

The decisions log names it: a `weather_days.rain_gauge_mm` column the app writes from a "Rain today" entry on the card; the skip uses the gauge when it is set and the model otherwise.

### 7.1 Checks on every push (S)

There is no `.github/`; the four checks run only by hand before a commit, and Vercel builds whatever is pushed. A workflow running `npm ci`, typecheck, lint, test and build on push is ten lines and catches a red push before it deploys.

### 7.2 Six helpers written several times (S)

`describeError` (Capture, DiagnosePanel, AskPanel, CheckScreen, SpeciesScreen), the `localStorage` read and write pairs (Today, Capture, Plants, i18n, leaflet), the `UUID` regex (diagnose, expand, ask, check), `missingTable` (`db.ts`, `_weather.ts`), the 1,000-row paging loop (`readAll`, `inventory`, `listAllPlants`, `listAllTasks`, `latestChecks`), `isNetworkFailure` (Capture, DiagnosePanel). One `src/lib/errors.ts`, one `src/lib/storage.ts`, one `api/_validate.ts`, and `readAll` shared by the app's readers.

### 7.3 Two untested seams (S)

`normalizeScientificName` and the three-step lookup in `api/profile.ts` decide whether a second olive costs a profile; `callJson`'s budget, the doubled retry and the transient retry decide whether a call is paid twice. Neither has a test; both are pure enough for one with a fake client.
