Deviations from `docs/SPEC.md` or `CLAUDE.md`, with the alternative taken. Newest first.

## 2026-10-29 — The spray line (0.8.1)

Mohamed asked why the weather card always showed "Spraying (savon noir, oils)". It did so by design: the line came up every day, whatever the round held. It also dropped today's windows once they had ended, so by late morning it read "today: no calm, cool, dry window" when the morning had been fine. Autumn days here are often calm until about 10:00 and gusty after, above the 25 km/h gust limit; the limits stay as they are.

- **The line shows only when something asks for a spray.** That is a pending scout, protect, prune or feed task, due today, overdue, in an open window or due tomorrow, whose title or instruction asks for a spray, or a plant's latest diagnosis from the last 14 days that does. A treatment is usually repeated over two weeks, and an older diagnosis of the same plant gives way to the newer one. Water, mulch, harvest and propagate tasks never count; a harvest instruction names a spray only for its waiting period. The line names up to three plants ("For FIG-01, OL-01", then "+N"). A diagnosis's re-photograph reminder is left out, since its title quotes the cause ("Spray scorch from savon noir") and the diagnosis counts on its own.
- **Diagnoses answer the question themselves.** The diagnose schema gets one more required field, `spray`: true when the treatment asks for a spray in the next two weeks, now or if the checks find the pest. Treatments must say "what to avoid", so a heat, water or salt diagnosis often names savon noir or oil only to rule it out, and wording alone misread many of them. Claude, which wrote the treatment, answers this exactly. Diagnoses saved before 0.8.1 have no answer; they count by wording, and only when the leading cause is a pest, a disease, a nutrient problem or "other".
- **Tasks count by wording.** The calendar items were written before this change, and adding a field would mean regenerating every profile and storing a new column, so a task is read for spray words. Those are the organic sprays the site uses (savon noir, soapy water, neem, the oils, Bordeaux mixture, copper fungicides, wettable sulphur, kaolin, Bt, spinosad, bicarbonate) and the verb, in English and French. A bare "oil", "huile", "copper" or "bordeaux" is left out ("olive oil", "rouge bordeaux"). The text is read clause by clause. A list of sprays stays one clause ("do not use neem, savon noir or white oil on the flowers"), and a dash or "and spray" starts a new one. A clause does not count when a refusal comes before the spray word ("do not spray", "avoid foliar sprays", "nothing to spray", "instead of sprays", "ne pas pulvériser"), or a deferral comes just before it ("hold off spraying", "skip the neem spray", "wait 3 days after a savon noir spray"). It also does not count when the clause says the spray is not wanted ("won't help", "would scorch the leaves", "not worth it", "keep savon noir off the flowers"). Limits ("no more than two sprays", "do not exceed 2 %"), same-day deferrals ("hold off until dusk"), repeats and conditions ("do not spray unless the colonies spread") still count.
- **How the wording rule was tested.** A review workflow wrote and judged some 290 realistic texts (treatments, cautions, pre-harvest intervals, heat, water and salt diagnoses, French edits). They are in `tests/data/spray-texts.json`, and the test fails if any of them changes reading. Ten known misreadings are listed in the test; most are harvest texts or heat diagnoses, which the task type and the diagnosis's answer already keep off the line. A blind set of 80 texts, written afterwards by an agent that had not seen the rule, read 73 right. All seven misses were false positives, and six of them were diagnoses (a spray put off to next season, already done, or ruled out at length), which new diagnoses settle with their own answer. The rule is still a heuristic: an unusual sentence can be misread, which is why the line names the plants it counted.
- **Today's windows are kept and marked.** A window that has ended reads "(passed)", the one under way "(now)", by the phone's hour; tomorrow's are listed as they are. Today used to read the hour again only on a return to the app, at midnight and after the 06:00 run; it now reads it on the hour as well, so the marks follow the clock while the screen stays open.

## 2026-10-26 — Phase 8: Weather for Menzel Bouzelfa

- **Weather is in scope now.** The spec listed weather feeds as out of scope for v1, and CLAUDE.md said to store nothing about it. The feature review of 2026-10-25 named it the one change that would make the reminders follow the season as the leading apps do, and Mohamed asked for it on 2026-10-26. CLAUDE.md's reminder-engine step 6 now describes what the run does with it.
- **Open-Meteo, no key.** Its forecast API is free for non-commercial use (a private app with no ads or subscriptions qualifies), needs no account, allows 10,000 calls a day, and asks for CC BY 4.0 attribution, which Today's card and the Settings card carry. The app makes two calls a day at most from the cron and one per app session at most from Today. If the farm's produce ever goes through a business that the app serves, the terms call for a paid plan.
- **One point for both sites.** The forecast is read for the mean GPS position of the farm plants within 30 km of Menzel Bouzelfa (a photo taken elsewhere is left out), otherwise for the town (36.683° N, 10.583° E). The backyard is a few kilometres away, inside the same forecast cell, so it shares the numbers.
- **Stored per date in `weather_days`.** The cron's rain skip needs yesterday's rain, Today's card needs the forecast without asking Open-Meteo on every opening, and the Claude calls need the same numbers, so one row per date is rewritten on each fetch (seven days back, seven ahead). `skipped` is the one column a fetch never writes: it holds what the 06:00 rain skip closed. One ★ SQL run; until then the cron reports the weather as unavailable and the rest runs as before.
- **The rain is Open-Meteo's model, not a gauge.** The forecast endpoint's past days are its archived model runs for the grid cell, so the skip can miss a local shower or count one that fell elsewhere; the Settings text says so and asks for a look at the soil after a shower. A rain gauge read into the app would be the fix if it matters.
- **The rain skip closes, it does not move.** At 06:00, after the expansion (so a watering it has just written for today is included), the periodic waterings due today or overdue are closed as skipped with the reason in the note (a watering window, a water rule with no interval, is left alone: closing it would end the season's reminder, since the expansion never writes a row twice), when the rain of the two days before today reaches the threshold (10 mm by default, 5 to 20 in Settings), or when today's forecast does at 70 % or more. Waterings due later keep their dates, so the rule's rhythm goes on; the journal shows each skip. A dry run (`?dry=1`) fetches and stores, counts what the skip would close for its message, and closes nothing. A second run the same day adds what it closes to the day's count. The setting falls back to its defaults only when the row or the table is missing; any other failed read stops the skip for the morning, so a skip the grower turned off is never turned back on by a bad read.
- **Today reads again after the 06:00 run.** Today loaded between midnight and 06:05 on the same date would keep showing the waterings the rain then skipped, so a return to the app, or a timer when the screen stays open, reads the list and the weather again after 06:05. A Done or Skip on a task that is no longer pending (closed by the skip, or on another screen) now changes nothing on screen but says so and reads again; it used to count a Done and offer an Undo that reopened the skipped watering. The threshold is one number for every plant: a per-plant water balance would need basin sizes and soil depth the app does not record.
- **Alerts with fixed thresholds and generic advice.** The figures are compared as the card shows them, rounded, so a day shown at 38° is a heat day. Each kind has two advice texts: one for preparing the day before, one for the day itself, since at 06:00 "the evening before" has passed. Heat at 38 °C; sirocco at 34 °C with the day's lowest humidity at 25 % or less and the dominant wind from 120° to 240° (a sirocco takes the place of a heat alert that day); frost at 2 °C, leaving a margin over the ground; a gale at 60 km/h gusts; heavy rain at a 30 mm forecast. The advice is the same for every plant (water young plants deeply the evening before, shade, stake, cover, open the basins), so no plant fact is written into the app; what a given species needs stays with Claude.
- **Spray windows from the hourly forecast.** Savon noir and oils scorch leaves in heat, drift in wind and wash off in rain, so a spray hour is one from 06:00 to 18:00 at 28 °C or cooler, wind 15 km/h or less, gusts 25 km/h or less, with no rain in it or the six hours after (an hour with no rain figure counts as wet); runs of two hours or more are kept, for today and the next two days.
- **One more push, not a longer digest line.** The site digests are about tasks and are left out when a site has none, but a sirocco matters either way, so the alerts of today and tomorrow and the rain skip go in a notification of their own (tag `weather`, so the next day's replaces it), sent before the digests. `sendDigest` now takes any message with a title, a body, a tag and a URL.
- **`/api/weather` for Today.** The card reads the table whenever Today reloads and, when today's row is missing or more than six hours old, asks the route (at most once every half hour) to fetch and store, then reads again; today's spray windows that have ended drop out; the route never skips waterings, which stays the cron's job. A failed refresh leaves the stored rows on screen.
- **Claude reads the weather.** Diagnose, Ask and the planting check get a block with the last seven days in one line (rain, extremes, alert days) and today and the next three days one line each, so heat scorch after a sirocco or a watering question after rain is read in context. The block says when the data was fetched, and that it is out of date when the last fetch is more than a day old. A missing table or a failed read gives "No weather data is stored" and never fails the paid call. The diagnose message changes for the first time since Phase 4.

## 2026-10-26 — Phase 7: Check before planting

- **A fifth Claude call, `/api/check`, rather than the profile's `site_fit`.** The profile already rates the species for Cap Bon in one sentence, but that rating is written once for every plant of the species and knows nothing of what is planted where. A check weighs the profile against the inventory as it stands (every plant by site and zone, the Settings zone lists, how many of this species there already are) and the site and zone in mind, and answers what a buyer needs: a verdict, eight factors, placement, planting time, buying tips, first-year care and alternatives. It follows the CLAUDE.md call conventions with `max_tokens` 4,096 at medium effort: eight factor notes and five sections are longer than an Ask answer; the doubled retry covers the rest. CLAUDE.md lists the budget.
- **The factors come before the verdict in the schema.** Structured output writes the properties in schema order, so the verdict follows the factor notes it should rest on. The card shows the verdict first. The eight factors are fixed (salinity, water, heat, cold, soil, animals, space, pests); `storedCheck` keeps that order and drops unknown or repeated entries.
- **"Not planted yet" is a species with no plant, not a new flag.** A typed name goes through `/api/profile` like Capture's "type a name". A name equal to a stored scientific or common name costs nothing; any other spelling ("Hass avocado" for a stored "Avocado") is profiled and the route then matches it to the species already kept, answering `created: false` with the tokens spent, so the screen shows the usage of every profile call that spent tokens, labelled for which case it was. A new species is kept with no plant. The library has always allowed a species with no plant (the species screen offers Delete for it, and its confirm now says the checks go with it); only Capture's abandoned captures deleted such rows automatically, and "Not planted yet? Check it instead" takes its species out of that clean-up. The Species tab's filter chips split the library on the plant counts it already reads.
- **Checks are kept, written by the app, like the Ask answers.** `planting_checks` holds every check of a species (site, zone, note and the result with its usage), so a re-check for the other site, or after the farm has filled up, sits beside the first. The id and `checked_at` are made on the phone: a retried save meets the unique id (`23505`) and counts as saved, a check answered after the screen was left is still written, and a save that failed gets one more try when the screen is left. Without the table (before the ★ SQL) the check still runs and the screen says it is not kept; the library and the species screen then show no verdicts. Deleting an unused species deletes its checks (`on delete cascade`).
- **The answer follows the app's language.** The check sends `lang` and the route asks for French text when the app is in French, keeping the enum values in English; profiles stay in English as before. A check read back shows the language it was written in.
- **A plant with no planting date is said to have none.** The reminders treat it as mature; in the check's "already recorded" line that would read as proof the species copes with the site, so it says "planting date unknown".
- **The zone cap is 200 characters.** A zone chip carries a Settings name, and Settings has no cap; the route takes up to 200 so a zone the app offered is never refused.
- **The library reads only the verdicts.** `latestChecks` selects `verdict:result->>verdict` beside the ids, since the table only grows and each result is a few KB of text; the species screen's card reads the full rows of one species. A failed read there shows "could not be loaded" with Retry; only a missing table reads as "not checked yet".
- **A paid check is not lost to a failed save.** Besides the unmount retry, "Check again" and "Check another plant" give a check whose save failed or is still out one more try before clearing it, a save that fails after the screen was left tries once more, and a late save answer for a check no longer on screen changes nothing (the save state is keyed on the row id).
- **The inventory, not the plant tags.** The message lists each zone's plants by species and count ("6 × Olive (Olea europaea)"), the Settings zones that are still empty, and the plants without a zone, farm first; tags add nothing to a placement and would lengthen the message with every plant. Zones are matched without case, as Ask does. The plants are read in pages of 1,000.
- **"Check this one" opens a prefilled check, it does not run one.** An alternative opens the check screen with its name, the same site and note; the grower taps Check, so a paid call never starts from a list item. The schema gives each alternative a `scientific_name` (the bare binomial) beside its display name, and the screen looks the species up by it, so an alternative already in the library (the prompt prefers species already recorded on site) costs no profile; editing the name drops the binomial. The screen is keyed on its query string, so each check starts clean.
- **No photo on the check screen.** At the nursery the name is on the label; a plant to identify goes through Capture, whose confirmed candidate leads to the check. Reading a label from a photo would duplicate identify.
- **Cost.** About 10 to 18 cents a check (3,000 to 6,000 input tokens, 1,500 to 2,500 output with the thinking), plus about 15 cents for a profile when the name is new to the library.

## 2026-10-25 — Review fixes (0.6.1)

A review of the whole app on 2026-10-25 (eight reviewers, each checked by a skeptic, then a pass over the seams) left 91 findings; the high and medium ones are fixed here, one commit each. Tests under `tests/` (vitest, `npm test`) cover the engine behaviours the fixes change.

- **The `/api` routes accept the owner only.** `verifyUser` now requires `OWNER_USER_ID` (★ the UUID of Mohamed's user under Authentication → Users, added in Vercel before this deploys) and answers 403 to any other signed-in account (not 401, which would sign the phone out), so the Claude key stays closed even if "Allow new users to sign up" is turned back on. The variable is required rather than optional: without it every route answers 500 "Server is not configured", which is visible at once, where a silent fail-open would not be. The table policies stay `using (true)`: with sign-ups off, every account is one Mohamed made, and a uuid checked into `schema.sql` would break a fresh setup.
- **The rule key of a periodic watering carries its interval.** CLAUDE.md keys tasks on `${type}:${months}:${age}`; a water rule with `every_days` now gets `:${every_days}` appended (`water:6-7-8:any:7`). Without it, changing the interval in the rule editor, or a regeneration writing a new one, kept the old schedule's pending waterings beside the new schedule for up to 90 days (every 3 days plus every 7 days, with back-to-back reminders). With the interval in the key the old rows are obsolete and go at the next expansion. One-time effect of the first run after this deploys: the pending waterings of the old key go as obsolete; those due today or later come back under the new key, so a watering already marked done that day comes back once, an overdue one is not replaced (the schedule's next watering is the next reminder), and a snoozed copy of a watering falls back to the regular schedule. Window rules are unchanged; the rule editor keeps its stricter check (type, months and age, without the interval).
- **The season's last watering closes itself.** The stale-watering rule closed a due watering only when a newer one of the same rule was also due, so the last watering of a season, left unacted, stayed in Today and the digest until the rule's months came round again (up to eight months of "Farm: 1 task"). The expansion now also closes the newest due watering of a rule once `every_days` (read from the key) have passed since it with nothing newer, as `skipped` with the note "Missed watering". Inside the season the next watering supersedes it on that same day, so nothing changes there. It counts under `superseded` in the expansion's response.
- **The expansion and the digest read in pages.** PostgREST stops every response at 1,000 rows, the service role included (the exports already page for that reason). The expansion's reads of the plants, the existing rows, the pending rows and the due rows, and the digest's read of the pending tasks, went in one request each, so past 1,000 pending rows (a summer of two- or three-day waterings for a few dozen young plants) the obsolete-rule cleanup saw an arbitrary 1,000 and left the rest, and the digest could miss a notice. `readAll` in `api/_tasks.ts` pages on a stable order (`id`, or `due_on` then `id`).
- **A finished window stays finished when its rule changes key.** The task identity is (plant, rule_key, due_on), and the key holds the months and the age. Editing a harvest rule from October–December to October–January, a regeneration writing other months, or a plant turning mature in the middle of a window made the expansion see a new rule and re-seed the open window as pending, next to the done row of the old key. The expansion now leaves out a seed for a window already open today when an acted row of the same plant and type, under a key that no longer applies, overlaps it and was acted on inside the new window (the Tunis day of `acted_at`): a done row, or a skip by the grower. The day of the action is what ties the two rows, since a plant carries several windows of one type (a scout rule per pest) and a done summer row must not swallow an autumn window re-keyed beside it; the price is that a harvest done in September under a September-to-November rule comes back when the rule becomes October-to-December. A window the expansion itself closed as ended does not count, so a rule extended after its window ended brings the window back, as it should. Nothing is written for the carried-over window: the check runs again each morning and stops with the window.
- **Two Claude-written rules with one key become one.** `profile.md` asked for "one item per action" and scout items per pest, so a profile could hold two scout items for the same summer months (olive fly and black scale, both June to October, age any). They share a rule key, so the expansion made a task for the first only, and the rule editor then refused to edit either, since each saw the other as its duplicate. The prompt now says so, and `api/profile.ts` folds such items into the first on every write (new profile and regeneration): titles joined with "; ", instructions appended, the largest lead and litres kept. The expansion folds the calendar it reads the same way, so a profile stored before this with such a pair gets one task carrying both titles and instructions (a window already pending keeps the first rule's wording until the next one); the stored pair itself stays until a regeneration (when the calendar is not under `user_edits`) or a hand edit, and the rule editor lets one of the pair be edited apart, where it used to refuse both as each other's duplicate.
- **Snooze counts from the task's own day, never lands on an acted row, stretches a window and holds back the waterings it skips.** The Phase 2 snooze added `days` to today whatever the task's date, and took any row already on that day as standing in. Reasoned for overdue tasks, that lost future ones: snoozing tomorrow's watering by one day collided with the task itself (ignored as 23505), closed it as snoozed and left nothing pending, which the expansion never recreated; a harvest due in a month snoozed one day moved to tomorrow. The new day is now `days` after the task's day, or after today when the task is overdue, and a day taken by a done, skipped or snoozed row is stepped past (up to a week, then the action fails with a message), so a snooze always leaves a pending reminder. Two more corrections of documented behaviour: the copy of a window task gets `window_end` moved to the new day when the snooze passes the window's end, so it is no longer closed as ended before the morning it was promised for (the "task expansion cleanups" entry said it would close that way); and snoozing a periodic watering closes the pending waterings between the two days as `snoozed` with the note "Covered by the snooze to …", since "snooze 7 days" on an every-3-days rule otherwise still rang on days 3 and 6. A task acted on since the screen loaded (Done on another screen, the expansion closing it) is not snoozed: the copy is taken back and the tap fails with "This task was already acted on". Today reloads after every snooze. Tests in `tests/db.test.ts`.
- **An open window is not overdue.** Window tasks are due on their window's first day and stay pending until acted on, so from the second day of every harvest, pruning or scouting window the Today header counted them as overdue, the week strip showed the dot, and they sorted above a watering that really was late, while the card itself read "Open since 1 Oct". `dueState` in `src/lib/today.ts` is now the one reading: late is a watering past its day or a window past its end; an open window is its own state. The header, the strip, the sort order (late, today, open, coming) and the cards use it. Today's round counts late and due-today tasks only, so "All caught up" and the leaves can come while a window stays open; before, they could not while any window was open, which in a food forest is most of the year.
- **Today follows the clock while it stays open.** The screen read the date, the hour and the streak once, when it mounted. The installed app sits in the background overnight, and a tap on the 06:00 notification focuses the open window without reloading it (the worker only navigates when the URL differs), so the morning after it still showed yesterday's date, greeting and round, listed today's tasks as "upcoming", left them out of the round and based a snooze on yesterday; only the tab badge, which already listened for the foreground, moved. Today now re-reads the clock whenever the app returns to the foreground and at the next midnight: the greeting, the scene and the streak follow at once, and when the date turned the list and the round are fetched for the new day and the day filter is cleared. The snooze already counts from the phone's date at the moment of the tap (previous entry).
- **Saves are written under ids made on the phone.** On a weak signal a write can reach Supabase while its reply is lost. The capture then showed "Failed to fetch" and Save again inserted a second plant (there is no unique key on plants besides the id), or re-chose the same storage path from the photo's EXIF time and Storage refused it for good ("The resource already exists"), leaving a plant with no photo and no way past it; a diagnosis's Save again did the same with its photo and could write a second re-photograph reminder. The Capture screen now makes the plant's id and each photo's id and path before the first write and keeps them for the attempt (`SaveProgress`); the plant and the photo rows are upserts on their id, and a path planned earlier is uploaded over (`upsert`). The diagnosis panel keeps its photo's path and id the same way, and a journal photo is uploaded over its path too (the path is past every photo row the screen knows, so an object already there is that photo's own earlier upload). A lost reply thus means the same rows written twice, which changes nothing. "Failed to fetch" now reads as the network message.
- **The back gesture closes a sheet, and a diagnosis is saved before the panel is looked for.** The diagnosis and Ask panels are React state over the Plant screen, not routes, so Android's back gesture, the usual way to dismiss a full-screen sheet, popped the router: the Plant screen and the panel unmounted, and a diagnosis answered after that was thrown away at the mounted check, with no photo row and no reminder, though Close had been disabled for exactly that reason (Phase 4). `useBackClose` pushes one history entry when a sheet opens and closes the sheet when it is popped; while a call or a save runs the entry is pushed back, so the sheet stays as the Close button would. Three details matter: the marker is added beside the router's own `history.state` fields (`idx`, `key`) rather than replacing them, or the router's later `replace` navigations lose their index; an entry already current is reused, so React's development double mount does not push twice; and the `back()` that drops the entry after a Close is deferred by a microtask and skipped when a sheet is mounted again at once. The Ask panel's profile link replaces the sheet's entry instead of pushing over it, so back from the profile returns to the plant in one tap. The app opens one sheet at a time; nested sheets would need an entry each. The diagnosis panel also starts the save before it asks whether it is still mounted, as the Ask panel already did, so a paid answer reaches the journal either way.
- **An unsaved answer is not lost without asking.** When the save of a diagnosis or of an Ask answer failed, Close was enabled again and threw the paid answer away without a word. Both panels now ask to confirm when something is unsaved (the back gesture asks the same way and keeps the sheet when declined), and the Ask panel gives each unsaved answer one more save on the way out whenever it is left another way, since the row needs nothing from the screen.
- **A plant can be deleted from its screen.** The spec has no removal, and a plant recorded under the wrong candidate, or a tree that died, kept receiving every rule's tasks on Today and in the digest with the Supabase table editor as the only way out. The Plant screen ends with a "Delete this plant" button behind a confirm: the row goes first (photos, tasks and questions cascade in the schema), then its files under `<plant id>/` in the bucket; a Storage failure after that leaves orphaned files only, and is not reported. The species profile stays. Moving a plant to another species is still a delete and a new capture.
- **Reminders read "On" only under the current push key.** The Settings card said On whenever the browser held any subscription, and Turn on reused it; the Phase 3 note that an older key pair "is dropped and replaced" described a branch that could never run, since `subscribe()` was only called when no subscription existed. After a VAPID rotation the phone therefore kept a subscription the push service answered with 403 every morning, while the card said On. `getPushState` now compares the subscription's key with the build's and reads an old one as Off; Turn on always calls `subscribe()`, which returns the current subscription or throws for a stale one, which is then dropped and replaced. The server logs a 403 as a key mismatch and keeps the row, since a misconfigured server key would otherwise delete every good subscription.
- **The digest's lines: notices, then late, today, open.** The body took the first three tasks by due date, so the one-day early notice of a window (always dated in the future) came after every due task and, with three or more waterings due, fell into "+N more" and was never read; long-open windows, dated at their start, likewise filled the three lines ahead of today's waterings. The lines now follow the same reading as Today: the early notices first (the one deliberate difference, since they come once), then what is late (a missed watering or an ended window), then due today, then the open windows, longest open first as on Today. The title's count is unchanged.
- **The Today badge is dark on apricot.** Its white figure, 12 px bold on the apricot tab badge, measured 2.7:1 in light mode and 2.2:1 in dark mode against the 4.5:1 text contrast asks for. The figure now uses the dark ink (`--sage-text`: 5.1:1 and 7.3:1); the apricot stays, since it is the colour that marks what is due across the app.
- **The tab badge counts like the round.** The Today badge counted pending tasks by due date, so with open windows left out of the round the badge read 5 where the round read 3 to go. `countDueTasks` now counts what is late or due on the day (a window that ended counts, one still open does not), the same reading as `dueNow`. The digest's title keeps counting every line it lists, open windows included, since each is a line of the message.
- **A Supabase Auth fault is not a sign-out.** `verifyUser` used to answer 401 for any error from `auth.getUser`, including a network failure or a 5xx from Supabase Auth, and the app drops its session on a 401 (`src/lib/api.ts`), so a blip between Vercel and Supabase signed the phone out and lost the capture in progress. Only a verdict on the token (auth-js's `AuthApiError` and its kin with a 4xx status) gives 401 now; every other error (`AuthRetryableFetchError`, an `AuthUnknownError` for a non-JSON reply, a 429, a 5xx) throws, and the route answers 502 or 500. A signed-in account that is not the owner's gets 403 with a plain message, not 401, so a mistyped `OWNER_USER_ID` shows as an error rather than a sign-out loop.

## 2026-10-25 — Phase 6: Ask Claude about a plant

- **A fourth Claude call beyond the spec.** The feature review of 2026-10-25 found that users of the leading apps value an expert or chatbot to ask; the spec's three calls answer only fixed questions (what is it, how to care for it, what is wrong). `/api/ask` follows the CLAUDE.md conventions (cached site context then call rules in `system`, structured output, the refusal fallback through `callJson`) with `max_tokens` 3,072 at medium effort. That budget is above diagnose's 2,048 because an answer of up to about 250 words plus medium-effort thinking needs more room than a diagnosis; the doubled retry still covers a long answer. CLAUDE.md lists the new budget.
- **The route only reads; the app saves.** As with a diagnosis, the answer goes to the phone first and the app writes the row under RLS. A question therefore works before the ★ SQL is run (the panel says the answers are not kept), and a failed save leaves the paid answer on screen with "Save again" instead of losing it. The row's id and `asked_at` are made in the browser when the answer arrives: a Save again after further questions keeps the exchange in its place in the thread, and a retry after an insert whose reply was lost meets the unique id (`23505`) and counts as saved instead of writing a duplicate. - **The Today badge counts due today or overdue on the phone's date.** The tab shows pending tasks with `due_on <= today` (Today itself lists the coming week as well). Since the review fixes (0.6.1) a window that is open is left out, as in today's round. It is counted again on every navigation, after Done, Skip or Snooze, after an expansion that changed the table (a window event from `src/lib/db.ts`) and when the app returns to the foreground. The same number goes to the app icon through the Badging API where Android supports it; nothing in the spec asked for it, but it costs three lines.

## 2026-10-24 — Phase 2 build

- **Snooze closes the row and opens a new one.** The spec says snooze moves `due_on`, but the expansion de-duplicates on (`plant_id`, `rule_key`, `due_on`): a moved row would free its slot and the next morning would recreate the task beside the snoozed copy. So `snoozeTask` inserts a new pending row for the same rule at the later date, then closes the current row as `snoozed` with `acted_at` set. That matches the schema: the `journal` view lists acted rows (so the snooze is logged, as spec block H asks) and the digest reads pending rows only. When the later date already holds a task of the same rule (a watering snoozed by 7 days when the rule is every 7 days), the unique constraint rejects the insert, the existing task stands in, and only the close happens. Superseded in part by the review fixes (0.6.1): only a pending task stands in, and an acted one is stepped past.
- **Snooze counts from today, not from `due_on`.** "Snooze 1 day" on a task overdue by a week means "tomorrow", so the new date is today + days. Superseded by the review fixes (0.6.1) for tasks due in the future, which count from their own day.
- **Windows are contiguous month runs, and an open window gets its task at once.** CLAUDE.md creates one task per rule on "the first day of the first month in `months` that falls in range" with `window_end` on the last listed month. Real profiles list separate windows in one rule (papaya feed in April, June and August; watering in April and October), which that reading would merge into a single April-to-August window. `api/_tasks.ts` splits `months` into contiguous runs on the 12-month circle ([11, 12, 1, 2, 3] is one run from November) and makes one task per run whose window overlaps the next 90 days: `due_on` the window's first day, `window_end` its last. A window already open today (a plant photographed in October while its harvest window runs October to December) gets a task dated at the window's start, shown as "Open since …" on Today, instead of waiting for next year; the dedupe key stays the same from one run to the next. The same `rule_key` serves every run of a rule; the runs differ by `due_on`.
- **Water tasks are anchored at the window's first day.** "Every `every_days`" needs a fixed origin or each daily run would compute different days. The series starts on the first day of the run (1 June, 8 June, … for every 7 days) and only the days from today to today + 90 are inserted, so a missed day is never backfilled.
- **Pending tasks of rules that no longer apply are removed.** After a profile regeneration the rule keys change, and when a plant passes 24 months (or gets a planting date) the stage changes; without a cleanup the old pending tasks would sit on Today for ever. The expansion deletes pending tasks of the plants it processed whose `rule_key` is not among the rules that apply at the plant's age. Done, skipped and snoozed rows are never touched, so the journal keeps its history.
- **`rule_key` months are sorted.** `${type}:${months.join("-")}:${age}` uses the months in ascending order whatever order Claude wrote them, so a regeneration that only reorders the list keeps the same key.
- **Litres in the water task title.** The task row has no litres column, and a watering reminder without the amount is half a reminder, so the expansion writes "Deep summer watering, mature tree (40 L)" as the title. The instruction is the rule's text unchanged.
- **"Today" is the Tunis date on the server.** Vercel runs in UTC; the cron at 05:00 UTC is 06:00 in Tunis, but `src/lib/dates.ts` computes the date in `Africa/Tunis` explicitly so a later schedule change cannot shift it. The app uses the phone's date. Dates travel as `YYYY-MM-DD` strings throughout.
- **Shared date and age helpers.** `src/lib/dates.ts` has no imports and is used by both the app and `api/` (which imports it as `../src/lib/dates.js`, like `src/types.ts`), replacing the two copies of the age calculation in `CalendarSection` and `PlantScreen`.
- **The expansion runs from the app too.** `/api/expand` (bearer token through `verifyUser`) runs the same `runExpansion` as the cron. The Capture screen calls it for the new plant before opening its screen, the Plant screen after a record edit, and Today once per app session plus on Refresh, so tasks never wait for 06:00. The cron remains the daily safety net.
- **`lead_days` waits for Phase 3.** Today lists tasks due within 7 days, which already shows a window a week ahead; the per-rule lead applies to the push digest.
- **Journal text for a skipped task is the reason.** The `journal` view shows `note` in place of the title when the note is set, so a skipped task reads as its reason under the type and status pills; done and snoozed tasks keep their title. Changing the view would need another SQL run, which the pills make unnecessary.

## 2026-10-23 — Phase 1 build

- **Thinking effort on Claude calls.** `claude-sonnet-5-5` thinks adaptively by default and bills thinking as output tokens, which also count against `max_tokens`. The identify call runs at `output_config.effort: "low"` (perception, not planning; keeps the 2,048-token budget for the JSON) and the profile call at `"medium"`. The returned usage includes `thinking_tokens` so the split stays visible. Raise identify to `"medium"` if identification quality disappoints.
- **Function time budget.** `vercel.json` sets `maxDuration: 300` (Fluid compute, the default for new projects, allows it on Hobby). `api/_claude.ts` keeps every call inside `FUNCTION_BUDGET_MS` (280 s): one request timeout equals the time left, the SDK's own retries are off, and the one retry on a transient error or on a cut output (`max_tokens`, doubled as CLAUDE.md asks) only runs when at least 60 s remain. If the Vercel plan rejects 300, lower `maxDuration` and `FUNCTION_BUDGET_MS` together (for example 60 and 55).
- **Bearer check before the method check.** Every route except `daily` answers 401 to any request without a valid token, whatever the method, so acceptance test 5 (open `/api/identify` in the browser) sees 401, not 405.
- **One profile per species, not per cultivar.** The lookup in `api/profile.ts` tries the exact (name, cultivar) pair, then the species-level row, then any row of the species, before calling Claude; otherwise a second photo of the same olive with fruit in frame (identify now returning a cultivar) would write a second profile. The identify output keeps the cultivar in `photos.ai_result`. Scientific names are normalised to the bare binomial (author citation and hybrid sign dropped) before lookup and insert, and both prompts ask for that form.
- **Regeneration resets `confirmed`.** A regenerated profile is new AI text, so the row goes back to "AI-written, confirm"; `user_edits` are re-read after the Claude call so a field saved during the wait is not overwritten, and the review screen disables editing while a regeneration runs.
- **Orphan species rows.** The profile call starts at Confirm, before the plant is saved, so an abandoned capture (Start over, Pick another, leaving the screen) would leave a species nobody uses. The Capture screen deletes a species it created when the capture is abandoned, and the species review screen offers Delete for a profile with zero plants. The foreign key from `plants` is the final guard.
- **Service worker updates prompt instead of reloading.** `registerType: "prompt"` with a "Reload" banner in the layout, because an automatic reload after a deploy would drop a photo mid-capture.
- **Storage policy in the schema.** `supabase/schema.sql` creates the private bucket and the `storage.objects` policy itself, so the SQL editor run is the whole database setup.
- **Refusal fallbacks not enabled.** The Anthropic SDK guidance suggests the server-side `fallbacks` parameter on Sonnet 5.5. CLAUDE.md says to surface a refusal to the user instead, and a fallback would run a model other than the one decided, so the parameter is left out. The identify and profile routes return `{ refusal, ...usage }` with HTTP 200 and the UI shows the text.
- **Prompt files on Vercel.** `api/_claude.ts` reads `prompts/*.md` and `*.schema.json` at runtime through `import.meta.url`, with `process.cwd()/prompts` as fallback, and `vercel.json` lists `prompts/**` in `functions.includeFiles` so the files ship with the functions.
- **`/api/daily` is a stub in Phase 1.** The cron entry in `vercel.json` needs a target, so the route exists and only checks `CRON_SECRET`; task expansion and the digest come in Phase 2.
- **SPA routing.** `vercel.json` rewrites every non-`/api/` path to `index.html` so deep links such as `/plants/<id>` open on the phone.
- **Profile edits are stored per top-level field.** `species.user_edits` keeps whole top-level JSON blocks (`water`, `uses`, …), not individual nested keys. A regeneration keeps those blocks verbatim. Editing `care_calendar` and `pests` by hand is deferred; regenerate instead.
- **i18n entry point.** All strings stay in `src/i18n/en.ts`; `src/i18n/index.ts` only exports the active table as `t`, where Phase 5 will pick `fr`.
- **Profile call timing.** The profile request starts when a candidate is confirmed, before the record form is filled, so the wait overlaps with typing. Save is disabled until the profile is ready.
- **Toolchain pins.** TypeScript stays on 5.9 because typescript-eslint does not support TypeScript 7 yet; Vite 8 and the current React 19 are used.
- **Photos in the journal.** Journal photos (kind `journal`) can be added from the Plant screen already in Phase 1; it costs nothing and fills the journal before tasks arrive.
