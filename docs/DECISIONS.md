# Decisions log

Deviations from `docs/SPEC.md` or `CLAUDE.md`, with the alternative taken. Newest first.

## 2026-10-25 — Review fixes (0.6.1)

A review of the whole app on 2026-10-25 (eight reviewers, each checked by a skeptic, then a pass over the seams) left 91 findings; the high and medium ones are fixed here, one commit each. Tests under `tests/` (vitest, `npm test`) cover the engine behaviours the fixes change.

- **The `/api` routes accept the owner only.** `verifyUser` now requires `OWNER_USER_ID` (★ the UUID of Mohamed's user under Authentication → Users, added in Vercel before this deploys) and returns null for any other account, so the Claude key stays closed even if "Allow new users to sign up" is turned back on. The variable is required rather than optional: without it every route answers 500 "Server is not configured", which is visible at once, where a silent fail-open would not be. The table policies stay `using (true)`: with sign-ups off, every account is one Mohamed made, and a uuid checked into `schema.sql` would break a fresh setup.
- **The rule key of a periodic watering carries its interval.** CLAUDE.md keys tasks on `${type}:${months}:${age}`; a water rule with `every_days` now gets `:${every_days}` appended (`water:6-7-8:any:7`). Without it, changing the interval in the rule editor, or a regeneration writing a new one, kept the old schedule's pending waterings beside the new schedule for up to 90 days (every 3 days plus every 7 days, with back-to-back reminders). With the interval in the key the old rows are obsolete and go at the next expansion. One-time effect of the first run after this deploys: every pending watering is re-keyed (deleted and created again), so a watering already marked done that day comes back once, and a snoozed copy of a watering falls back to the regular schedule. Window rules and the rule editor's duplicate check are unchanged.
- **The season's last watering closes itself.** The stale-watering rule closed a due watering only when a newer one of the same rule was also due, so the last watering of a season, left unacted, stayed in Today and the digest until the rule's months came round again (up to eight months of "Farm: 1 task"). The expansion now also closes the newest due watering of a rule once `every_days` (read from the key) have passed since it with nothing newer, as `skipped` with the note "Missed watering". Inside the season the next watering supersedes it on that same day, so nothing changes there. It counts under `superseded` in the expansion's response.
- **The expansion and the digest read in pages.** PostgREST stops every response at 1,000 rows, the service role included (the exports already page for that reason). The expansion's reads of the plants, the existing rows, the pending rows and the due rows, and the digest's read of the pending tasks, went in one request each, so past 1,000 pending rows (a summer of two- or three-day waterings for a few dozen young plants) the obsolete-rule cleanup saw an arbitrary 1,000 and left the rest, and the digest could miss a notice. `readAll` in `api/_tasks.ts` pages on a stable order (`id`, or `due_on` then `id`).
- **A Supabase Auth fault is not a sign-out.** `verifyUser` used to answer 401 for any error from `auth.getUser`, including a network failure or a 5xx from Supabase Auth, and the app drops its session on a 401 (`src/lib/api.ts`), so a blip between Vercel and Supabase signed the phone out and lost the capture in progress. Those errors (auth-js's `AuthRetryableFetchError`, 429 and 5xx) now throw, and the route answers 502 or 500; only a rejected token gives 401.

## 2026-10-25 — Phase 6: Ask Claude about a plant

- **A fourth Claude call beyond the spec.** The feature review of 2026-10-25 found that users of the leading apps value an expert or chatbot to ask; the spec's three calls answer only fixed questions (what is it, how to care for it, what is wrong). `/api/ask` follows the CLAUDE.md conventions (cached site context then call rules in `system`, structured output, the refusal fallback through `callJson`) with `max_tokens` 3,072 at medium effort. That budget is above diagnose's 2,048 because an answer of up to about 250 words plus medium-effort thinking needs more room than a diagnosis; the doubled retry still covers a long answer. CLAUDE.md lists the new budget.
- **The route only reads; the app saves.** As with a diagnosis, the answer goes to the phone first and the app writes the row under RLS. A question therefore works before the ★ SQL is run (the panel says the answers are not kept), and a failed save leaves the paid answer on screen with "Save again" instead of losing it. The row's id and `asked_at` are made in the browser when the answer arrives: a Save again after further questions keeps the exchange in its place in the thread, and a retry after an insert whose reply was lost meets the unique id (`23505`) and counts as saved instead of writing a duplicate. If the panel goes away while Claude answers (the back gesture, the profile note's link; Close itself waits), the answer is still saved, since it has been paid for.
- **The app carries the conversation.** Each question goes with the earlier exchanges of the panel, of which the route reads the last six, each answer cut at 2,000 characters, written into the one user message ("Grower: … / You: …") ahead of the question. `callJson` keeps its single-message shape, and caching is unchanged since the cached part is the system prompt. Questions asked in other conversations about the same plant are not sent: the journal keeps them, and a conversation reopened from it continues with its own history.
- **The context is the plant's, not the species'.** Besides what a diagnosis gets (the species block, pests, plant line, the tasks acted on in the last 30 days and the overdue ones), the message carries the care calendar rules, companions, uses and toxicity, whether the profile is confirmed and which blocks were edited by hand, the other plants of the zone, the last time each kind of task was marked done whatever the date (the last watering, and a scan of the 200 newest other done rows, enough for years of pruning and feeding), the pending tasks due in the next 30 days, and the last three diagnoses with their leading cause, the grower's note and the treatments logged from them (`diagnosis:<photo_id>:treated` rows). The lists have limits (30 recent, 20 coming, 30 neighbours); a list cut by its limit says so, and the prompt tells Claude what the records cover and to say "the app has no record of" rather than assume care was not given, since a feed or a pruning is often older than 30 days. Zones are free text, so the neighbours are matched without case in the function over at most 500 plants of the site, rather than with PostgREST's `ilike`, whose `%`, `_` and `*` are wildcards.
- **Shared context helpers.** The text blocks moved from `api/diagnose.ts` to `api/_context.ts` and both routes use them. The diagnose message was compared byte for byte on a fixture before and after the move, so diagnoses are unchanged.
- **Three output fields.** `answer` is plain text (paragraphs and "- " lists, shown with its line breaks kept); `profile_note` names a field of the profile the answer disagrees with, shown as a warning with a link to the species screen, and nothing changes the profile by itself: the grower edits it if convinced; `follow_ups` are up to three next questions shown as chips that fill the text box without sending, since every question is a paid call. The answer's language follows the question; the starter questions follow the app language.
- **No photo in Ask.** A symptom goes to Diagnose, which already stores the photo, logs the treatment and sets the follow-up reminder; Ask would duplicate that flow. The intro says so. A photo question (ripeness, a bud) can follow if it is missed.
- **Refusals are shown, not saved.** A declined question leaves no row; the usage of the declined call shows under it.
- **One row per exchange in a new `questions` table.** `thread_id` groups a conversation and is made in the browser (`crypto.randomUUID`) when the first answer arrives; `answer` keeps the JSON and its usage, like a problem photo's `ai_result`. One ★ SQL run creates it. Until then reads and writes raise `QuestionsUnavailable`, which the panel turns into the notice and the Plant screen into "no answer previews"; the Journal itself is untouched.
- **The `journal` view lists questions and now runs with `security_invoker`.** Supabase views run as their owner unless `security_invoker` is set, so the Phase 1 view bypassed the tables' RLS and answered the public anon key with every journal row (photo notes, task titles and notes, skip reasons). The rebuilt view, which the questions arm required anyway, reads the tables with the caller's rights: the signed-in user sees everything as before, and a request with the anon key alone sees nothing (any signed-in account still sees everything, hence the sign-ups check below). PHASE6.md's test 7 checks it from the SQL editor. `create or replace view` keeps the six columns in order and type, so the app's reader is unchanged; a question's `ref` is the row id, which the Journal tab maps to the answer preview.
- **The journal's question rows carry their thread id.** The view puts it in `subtype` (the photo kind or task type in the other arms), so "Open the conversation" works from the journal row alone; the answers read from `questions` only add the previews, and their failure is swallowed.
- **Sign-ups must be off.** `verifyUser` and every policy (`to authenticated using (true)`) trust any signed-in user, which holds only while the project has one user. Supabase leaves "Allow new users to sign up" on by default, and the anon key ships in the app, so PHASE6.md adds a ★ check that it is off. Pinning the owner in code (an owner id checked by `verifyUser` and the policies) would close it for good; it is left as a follow-up since it changes every route and policy.
- **Cost.** About 9 to 18 cents a question at Fable 5.1 prices (4,000 to 8,000 input tokens, 1,000 to 2,000 output with thinking), most of it output. The site context is a cache read only within five minutes of the previous call (the default TTL). The panel shows the uncached input and the output under each answer.

## 2026-10-25 — UI refresh

- **An icon package despite "no component library".** `lucide-react` is line icons only (ISC), imported by name so the bundle carries the forty or so in use. Drawing them by hand would have cost time and consistency. The emojis in the tab bar and on the camera button are gone. Each task type and site has one icon and one colour pair (`src/lib/icons.ts`, `--c-<type>` tokens), used by the task cards, the week strip, the journal and the lists.
- **One display face, self-hosted.** Fraunces 600, latin subset, from `@fontsource/fraunces` (an 18 KB woff2) is imported in `main.tsx` and precached by the service worker, so headings look the same offline. Google Fonts was not used, because it would add a third-party request at every cold start and fail offline. Body text stays on the system font, so Arabic names keep the phone's Arabic font.
- **The capture button moves into the tab bar.** The floating button covered the actions of the last card on every list. The bar now has five slots, with the camera raised in the middle as in the reference screenshot.
- **"This week" is today plus six days.** The list used to read up to today + 7 (eight days). The strip has seven columns, so the list now reads to today + 6 to match. A 7-day snooze lands just outside the list, which is not read again for it, as before.
- **The streak counts check-ins on this phone.** A streak of tasks done would break on the many days nothing is due between waterings. A streak worked out from the tasks table would need the history of what was due each day, which the table loses once rows are snoozed or removed. So the streak counts the consecutive days Today was opened, kept in `localStorage["plantcare.checkins"]` (last 120 days), and shows from 2 days on. It belongs to the phone and resets if the site data is cleared.
- **Today's round counts tasks done since midnight on the phone.** "Done" is the rows with status `done` and `acted_at` after local midnight (`countDoneSince`). A treatment logged from a diagnosis counts too, since it is care done today. The total is done plus the pending tasks due today or overdue. Skipped and snoozed tasks leave the total.
- **Undo for Done and Skip, not for Snooze.** Undo sets the row back to `pending` and clears `acted_at` and `note` (`reopenTask`, which only touches a done or skipped row). A snooze wrote a second row, or found one already on that day, and closed the first as `snoozed`. Undoing it would mean deleting a row the expansion's de-duplication may rely on, so the snooze toast only names the new day.
- **The card ticks at once, and the row leaves after the save.** Done marks the card straight away. The row is removed once both the save and the 0.8 s fold have finished. On an error the card comes back and the error banner shows. Under `prefers-reduced-motion` the wait is zero and the animations, the burst and the leaves are off. The vibration (`navigator.vibrate`) is skipped there too.
- **No weather.** The reference shows a weather strip; `CLAUDE.md` keeps weather out of scope, so the 7-day strip shows each day's task count and main task type instead.
- **The garden scene follows the phone's clock.** The scenes run dawn 5–9 h, day 10–16 h, dusk 17–19 h and night 20–4 h. The greetings run morning 5–11 h, afternoon 12–16 h, evening 17–21 h and night 22–4 h. The sky looks the same in light and dark mode, and the scene fades into the page colour at its foot. It is inline SVG, with no image file.
- **The Species screen and the profile sections keep their markup.** The Phase 5 calendar and pest editors were written there at the same time, on `main`, so this branch left those files alone until it merged `main`. The editors pick up the new palette through the shared classes (buttons, pills, the month picker's accent). The only change there is the care-calendar card's type pill, now the coloured `TypePill`, with the watering interval and litres in the water colour.

## 2026-10-25 — Claude Fable 5.1

- **The three Claude calls run on Claude Fable 5.1 (`claude-fable-5-1`).** Mohamed asked for the most capable model on the Claude API; it replaces the `claude-sonnet-5-5` that CLAUDE.md and the spec name. `MODEL` in `api/_claude.ts` sets it for identify, profile and diagnose, so going back is a one-line change. List prices are $10 per million input tokens and $50 per million output tokens, five times Sonnet 5.5, with cached reads at $0.25 per million: about 5 cents per photo identified, 15 cents per new species profile and 5 to 10 cents per diagnosis, so the spec's first-year estimate rises from under $5 to under $25. Fable 5.1 needs the Claude organisation on the default 30-day data retention; an organisation set to zero data retention gets HTTP 400 on every call.
- **Effort and token budgets are unchanged.** Fable 5.1 counts tokens with the same tokenizer as Sonnet 5.5 and thinks before answering as Sonnet did here, so the budgets set for Sonnet should still fit: identify at low effort with 2,048 tokens, profile at medium with 6,000, diagnose at medium with 2,048, each with the one doubled retry. Anthropic's guidance is that Fable's low and medium settings often exceed earlier models at their highest, and more effort means longer calls inside the 280 s function budget. If the Console shows the doubled retry becoming common, raise the first budget; if answers still fall short, raise that route's effort to `high`.
- **Refusal fallbacks are on, replacing the Phase 1 entry "Refusal fallbacks not enabled".** Fable 5.1 runs extra safety classifiers aimed at research biology and cybersecurity, and Anthropic warns they occasionally decline benign life-sciences work, which pest and disease questions sit close to. Every call now goes through `client.beta.messages.create` with `fallbacks: "default"` and the beta header `server-side-fallback-2026-07-01`, so a declined call is re-run inside the same request on the fallback model Anthropic picks for that refusal category. The `model` of each response, which a profile stores as `species.generated_by`, names the model that actually answered, so a fallback stays visible. When the whole chain declines, the route still returns `{ refusal }` and the UI shows it, as CLAUDE.md asks. After a fallback the token counts include the declined attempt, read from `usage.iterations`. Deleting the `betas` and `fallbacks` lines in `callJson` turns it off.
- **Prompts unchanged; calls stay non-streaming.** The prompts state goals and constraints rather than steps, which suits Fable 5.1, and none asks Claude to write out its reasoning, which Fable may refuse as reasoning extraction; the one- or two-sentence `evidence` fields are the short explanation it allows. Each call returns one JSON answer bounded by `max_tokens`, and the request timeout is already the time left in the 280 s budget, so streaming would change nothing the phone sees.

## 2026-10-24 — Phase 5 build

- **Switching the language reloads the app.** `t` is a module constant imported by every screen and helper (`src/i18n/index.ts` picks `en` or `fr` once, when the module loads), so a change cannot propagate without a re-render of everything. Rather than turn every import into a React context (some thirty files, plus module-level tables such as the tab list in `Layout.tsx`), the Language card stores the choice under `localStorage["plantcare.lang"]` and calls `window.location.reload()`; the service worker serves the shell from its cache, so the reload works offline. Without a stored choice, `navigator.language` starting with `fr` gives French, anything else English. `<html lang>` is set from the same value at load.
- **`as const` dropped from `en.ts`.** With it, `Strings` was a type of string literals ("Today", "Plants") that no French text could satisfy. Every literal now widens to `string`, and `fr.ts` is declared `const fr: Strings`, so a key missing, misspelt or added on one side only fails `npm run typecheck`. Nothing in the app relied on the literal types (`keyof typeof t.plant.tabs` still works).
- **The digest and the expansion notes stay English.** `api/_push.ts` and `api/_tasks.ts` import `en` directly; the server has no access to the phone's stored choice, and the one place it could read one, the new `settings` table, would make the digest depend on a row that may not exist yet. Left as a follow-up: a `lang` row in `settings` read by the cron. The French table carries the `digest` and `expansion` keys all the same, so the type stays whole.
- **Dates follow the phone's locale, not the app language.** `toLocaleDateString()` is called without a locale throughout; a phone set to English shows "Oct 24" under French labels. Passing the app language as the locale would touch every date call for a cosmetic gain; left as is.
- **Text the app writes is in the language of the moment.** The follow-up task titles and the "Treated: …" notes of a diagnosis come from `t` when they are written, so a diagnosis made in French leaves French rows in `tasks`. The Claude-written profile text, the task titles the expansion copies from the care calendar and the identify candidates keep the language Claude wrote them in (English, per the prompts); translating them is out of scope.
- **The exports carry raw database values under stable column names.** Site `farm`, source `nursery`, status `done`, dates as `YYYY-MM-DD`, the ids included, `snake_case` headers: the file is the same whatever the app language, Excel sorts the dates as dates, and the rows can be matched back to the tables. Only the Settings card's text is translated. The plants file adds the tag, quantity, rootstock and the four species names to the columns the spec names; the tasks file adds the title, instruction, rule key and site, and includes done, skipped and snoozed rows, since it is the log and not the to-do list.
- **Whole tables, read in pages.** PostgREST answers at most 1,000 rows per request. `listAllPlants` and `listAllTasks` in `src/lib/db.ts` page through with `range()` on a stable order, so a tasks table past that mark (a year of waterings for a hundred plants) still exports whole; the screens keep their single-request readers.
- **Download through an anchor.** `<a download>` on a Blob URL is what Android Chrome supports from an installed PWA; the file lands in Downloads under a dated name. The UTF-8 byte-order mark makes Excel decode the Arabic names; Sheets and LibreOffice ignore it. Line ends are CRLF and cells are quoted per RFC 4180 (quotes doubled; commas, quotes, line breaks and outer spaces trigger quoting).
- **Zones live in a `settings` table rather than being derived from plants.** A list derived from the plants cannot hold a zone before its first plant is recorded, cannot be ordered, and cannot be cleaned (a typo in one record is a zone for ever) without editing each plant; and the spec's Settings row says "Sites and their zones … edit lists". The table is generic key/value (`key text primary key, value jsonb`, the same `owner_all` policy as the other tables), so a later setting such as the digest language needs no further SQL run. It is the one schema change of the phase and asks Mohamed for one SQL run (the ★ step in `PHASE5.md`). The record form still reads the recent zones from the plants and keeps them in the field's suggestion list, after the listed ones; removing a zone from the list changes no plant, since the zone stays free text on the record as Phase 1 decided. Sites remain the two enum values of the schema: a third site would be a schema change, a prompt change and a `site_t` migration.
- **The app works before the SQL is run.** A read or write of `settings` that fails with PostgREST's "table not found" (`PGRST205`) or Postgres `42P01` raises `SettingsUnavailable`; the Settings card shows the instruction to run the ★ SQL instead of an error, and the record form shows no chips.
- **The care calendar and the pests are edited by hand, one entry at a time, and saved as whole lists.** Phase 1 left both read-only ("regenerate instead"). The species screen now gives each rule and each pest card an Edit button and each section an Add button; the form opens in place of the card, with Save, Cancel and Delete (behind a confirm). On a phone the months are twelve toggles in two rows of six (`MonthPicker`), numbers are typed as text so a field can be emptied first, and the watering fields show for water rules only. One editor is open at a time on the whole screen, and none while a regeneration runs. A save writes the whole list through `updateSpeciesField`, so `user_edits` holds the list under `care_calendar` or `pests`, the card shows "edited by you", and `api/profile.ts` keeps it on regeneration with no server change, since its merge already covers every top-level key.
- **An edited list is no longer refreshed by a regeneration.** `user_edits` keeps whole top-level blocks (the Phase 1 rule), so one changed rule pins the entire calendar; the card says so under the list. There is no button to hand a list back to Claude; until there is, that means clearing the key from `species.user_edits` in the Supabase table editor and regenerating. Left as a follow-up.
- **A calendar save expands the tasks at once.** After a care calendar save the screen runs `/api/expand` for every plant (skipped when no plant uses the profile) and shows its progress under the list; the cron does the same the next morning anyway. A change of type, months or age changes the `rule_key`, so the old pending tasks are removed and new ones created. A change of title, instruction, litres or warning only keeps the `rule_key`: tasks already pending keep their old wording, and the new text reaches the tasks created after, since the expansion de-duplicates on plant, rule key and day and never rewrites a pending row. Pest edits change no task: scouting tasks come from the calendar's `scout` rules, not from the pests list.
- **Two rules alike in type, months and age are refused.** They would share one `rule_key`, and the expansion would make one task for both. The form says so instead of saving.
- **One ordering for display and editing.** `src/components/profile/order.ts` sorts rules (first month, then task type) and pests (first month) as indices into the stored list, so `CalendarSection`, `HealthSection` and the editors list them alike and an Edit maps back to the right row. `RuleCard` and `PestCard` are exported with an optional actions slot rather than copied.
- **ESLint ignores `.claude`.** Other sessions' worktrees live in `.claude/worktrees/`, each a full checkout with its own `eslint.config.js` and, for some, its own `node_modules`; ESLint 10 looks up the config per file, so `npm run lint` from the main checkout loaded two configs and typescript-eslint stopped on "multiple candidate TSConfigRootDirs". The main checkout never needs to lint them.

## 2026-10-24 — Dropping `@vercel/node`

- **The Vercel request and response types come from a local file.** `@vercel/node` was a dev dependency used for the `VercelRequest` and `VercelResponse` types only. Vercel's Node runtime builds and runs the functions under `api/` with its own copy of the builder, so the package was never needed at run time, and the six `npm audit` findings (undici, path-to-regexp, and ajv through `@vercel/static-config`) travel with every release since 2.1.1, the newest (27.0.2) included, so no bump clears them; the "`@vercel/node` stays on 27" entry of the task expansion cleanups left this for a later pass. `api/_http.ts` now declares the two types over Node's `http` module: `IncomingMessage` plus `query`, `cookies` and `body` (typed `unknown`, so each route keeps narrowing it), and `ServerResponse` plus the chaining `status`, `json` and `send`, the members the routes use and nothing more. Every route imports them from `./_http.js` and the package is gone from `package.json`. The one finding left after that, ajv 8.6.3 reached through `vite-plugin-pwa` and `workbox-build`, went with `npm audit fix`: a lock-only move to ajv 8.20.0 inside workbox-build's own range, so `npm audit` reports no findings.

## 2026-10-24 — Task expansion cleanups

- **Ended windows close themselves.** The spec and CLAUDE.md leave a window task pending until it is acted on; Today showed it as "Window ended …" for ever and the digest listed it every morning. The expansion (`/api/daily` and `/api/expand` alike) now closes a pending window task whose `window_end` is before today as `skipped`, with `acted_at` set and the note "Window ended", so it leaves Today and the digest and keeps its line in the plant's journal (the `journal` view lists acted rows and shows the note in place of the title). The "Window ended" label on Today stays for the hours between a window's end and the next expansion run. A window task snoozed past its own end closes the same way on the next run.
- **Stale waterings collapse to the newest.** Water rules make one task per interval, so a week away left one overdue watering per missed interval on Today and the digest nagged about each. When a plant has several pending waterings of the same `rule_key` due on or before today, the expansion keeps the newest pending and closes the older ones as `skipped` with the note "Superseded by the next watering". Waterings due after today are not looked at. Nothing in the spec covered this.
- **One pure function, run after the insert and the obsolete-rule cleanup.** `staleTasks` in `api/_tasks.ts` takes task rows and returns the ids to close; `runExpansion` feeds it the pending rows due on or before today, read in a query of its own after the deletes, and closes them with `status = pending` as a guard so a task acted on from the phone in between keeps its status. Done, skipped and snoozed rows are never touched, nor rows whose `rule_key` starts with `diagnosis:` (Phase 4 may add those). The two notes come from `src/i18n/en.ts` like the digest text. Both routes return the counts as `expired` and `superseded`, and the Today refresh note shows them.

## 2026-10-24 — Phase 4 build

- **Diagnosis rows are the one kind of task the app writes.** The schema comment said tasks are "never typed by hand", and the expansion removes pending tasks whose `rule_key` is not an applying rule of the species. A diagnosis writes two rows from the app: the re-photograph reminder (a pending `scout` row, `rule_key` `diagnosis:<photo_id>`) and each treatment (a done `protect` row, `rule_key` `diagnosis:<photo_id>:treated`, note "Treated: …" so the `journal` view shows it). `runExpansion` in `api/_tasks.ts` skips rows whose `rule_key` starts with `diagnosis:` when it removes obsolete tasks, one delimited check; the schema comment is updated (a comment only, no SQL run). The treated row carries its own suffix because the unique constraint is (plant, rule_key, due_on): a treatment logged on the day the reminder comes due would otherwise collide with it.
- **The reminder is written at save time, not on a tap.** When the diagnosis says `rephotograph_in_days` is 1 or more, the scout task is created right after the photo row; the card shows its state (set for a date, done, skipped) and offers "Set the reminder" only when none exists. Days are clamped to 1 to 365; 0 or less means no follow-up photo.
- **Pest scouting from a diagnosis changes the wording only.** When the leading cause is a pest with likelihood 0.5 or more, the follow-up task reads "Scout <tag> for <pest>" with a check-the-plant instruction; otherwise "Re-photograph <tag>: <cause>" with the first check. The cause in a title is cut at its first comma, colon or bracket and at 60 characters (`shortCause`): Claude writes causes as whole sentences, and the first live run produced a title of 120 characters, too long for a digest line. Feeding a confirmed pest back into the species `pests` list is left out: `pests` is a Claude-written profile block kept verbatim by `user_edits` on regeneration, and an automatic append from a 0.5-likelihood guess would stick to every plant of the species. Regenerating the profile is the way to update that list.
- **`ai_result` of a problem photo is the diagnosis, its usage and the note.** Identify photos store the whole identify response; a problem photo stores the diagnosis plus the usage fields and the grower's note. The note also goes to `photos.note`, so the `journal` view shows it as the entry text without a change to the view, and the journal entry adds the urgency pill and the summary from `ai_result`.
- **One photo per diagnosis in the app.** The route accepts 1 or 2 images like identify, but the panel sends one: a second `problem` row without a diagnosis would show as a bare entry in the journal. "Another photo" replaces the first before sending.
- **The photo is saved after Claude answers.** Upload and row insert run once the diagnosis is in, so a failed or refused call leaves nothing in Storage. If the save fails the result stays on screen with "Save again" (the upload is not repeated), and the treatment and reminder buttons wait for the row.
- **Context tasks: acted in the last 30 days, plus pending due up to today.** "The last 30 days of tasks" is read as what was done, skipped or snoozed in that time plus what is still pending (overdue, or an open window), newest first, at most 30 rows; pending tasks in the future say nothing about the problem. Today's date and month open the text, since a diagnosis is seasonal. A previous treatment logged from a diagnosis appears in that list, so a follow-up diagnosis knows what was applied.
- **Image validation shared.** `parseImages` moved from `api/identify.ts` to `api/_images.ts` so both routes validate the same way; identify's behaviour is unchanged.
- **Close is disabled while a call runs.** A diagnosis costs a Claude call; the panel keeps Close off while preparing, sending or saving so the paid answer is not dropped by a stray tap.
- **Effort medium at `max_tokens` 2048, as CLAUDE.md asks.** Thinking counts against `max_tokens`; `callJson` retries once at 4,096 when the first attempt is cut. If the Console shows the retry becoming common, raise the first budget rather than lower the effort.

## 2026-10-24 — Phase 3 build

- **The push handler joins the generated worker through `importScripts`.** `vite-plugin-pwa` stays in `generateSW` mode (precache and the "Reload" prompt unchanged); `public/push-sw.js` holds the `push` and `notificationclick` listeners and `workbox.importScripts` pulls it into `dist/sw.js`. Switching to `injectManifest` would have meant a second build and a hand-written precache for two small listeners. The file is plain JavaScript served from `public/`, so it is outside the TypeScript and ESLint passes; it is kept short for that reason. It is excluded from the precache (`globIgnores`) since the browser already caches imported worker scripts and checks them for updates with the worker.
- **The early notice goes out on one day, without a column.** CLAUDE.md asks for window tasks `lead_days` early "once". Rather than a `notified_at` column (another SQL run), the digest includes a window task on the single day that is exactly `lead_days` before its `due_on`, then again from its due date on while it is pending. A cron run missed on that one day loses the early notice only; the due-date notice still comes. Water tasks never get an early notice (they repeat every few days). A task whose rule is gone from the calendar (the expansion removes it on its next run) counts as lead 0.
- **Digest lines carry the plant tag.** Task titles are species-level ("Harvest persimmons"), so each of the three body lines reads "title · tag", a fourth line says "+N more", and an early notice reads "From 1 Nov: …". The title stays "Farm: 6 tasks" as CLAUDE.md says. Farm comes before Backyard, as on Today, and a site with nothing due sends nothing.
- **The digest text comes from `src/i18n/en.ts`.** The function imports the same string table as the app (`tsconfig.json` now includes it) so the French toggle of Phase 5 can switch the notifications too; `en.ts` has no imports, like `types.ts` and `dates.ts`.
- **A missing VAPID variable does not fail the cron.** The expansion runs first; if subscriptions exist but a VAPID variable is missing or malformed, `/api/daily` still answers 200 with the counts and a `digest_error`, so tasks keep flowing while the keys are being added. With no subscription at all the digest is skipped silently and the keys are never read.
- **`?dry=1` on `/api/daily`.** With the cron secret it composes the digest and returns it without sending, so the content can be checked from the server without a notification on the phone. The expansion still runs.
- **Subscriptions are rows, not users.** `push_subscriptions` has no user column (one user); the route keys on `endpoint` and upserts, so re-subscribing from the same phone replaces the row. `POST { unsubscribe: true, endpoint }` and `DELETE` both remove it. A push service answer of 404 or 410 deletes the row during the send.
- **Turn on subscribes in the browser first, Turn off removes the row first.** If the server rejects a new subscription the browser subscription is removed again, and if the row cannot be deleted the browser stays subscribed, so the Settings card never says "On" for a phone the digest cannot reach, nor "Off" for one it still reaches. A subscription made with an older key pair (`InvalidStateError` on subscribe) is dropped and replaced.
- **The Today badge counts due today or overdue on the phone's date.** The tab shows pending tasks with `due_on <= today` (Today itself lists the coming week as well). It is counted again on every navigation, after Done, Skip or Snooze, after an expansion that changed the table (a window event from `src/lib/db.ts`) and when the app returns to the foreground. The same number goes to the app icon through the Badging API where Android supports it; nothing in the spec asked for it, but it costs three lines.

## 2026-10-24 — Phase 2 build

- **Snooze closes the row and opens a new one.** The spec says snooze moves `due_on`, but the expansion de-duplicates on (`plant_id`, `rule_key`, `due_on`): a moved row would free its slot and the next morning would recreate the task beside the snoozed copy. So `snoozeTask` inserts a new pending row for the same rule at the later date, then closes the current row as `snoozed` with `acted_at` set. That matches the schema: the `journal` view lists acted rows (so the snooze is logged, as spec block H asks) and the digest reads pending rows only. When the later date already holds a task of the same rule (a watering snoozed by 7 days when the rule is every 7 days), the unique constraint rejects the insert, the existing task stands in, and only the close happens.
- **Snooze counts from today, not from `due_on`.** "Snooze 1 day" on a task overdue by a week means "tomorrow", so the new date is today + days.
- **Windows are contiguous month runs, and an open window gets its task at once.** CLAUDE.md creates one task per rule on "the first day of the first month in `months` that falls in range" with `window_end` on the last listed month. Real profiles list separate windows in one rule (papaya feed in April, June and August; watering in April and October), which that reading would merge into a single April-to-August window. `api/_tasks.ts` splits `months` into contiguous runs on the 12-month circle ([11, 12, 1, 2, 3] is one run from November) and makes one task per run whose window overlaps the next 90 days: `due_on` the window's first day, `window_end` its last. A window already open today (a plant photographed in October while its harvest window runs October to December) gets a task dated at the window's start, shown as "Open since …" on Today, instead of waiting for next year; the dedupe key stays the same from one run to the next. The same `rule_key` serves every run of a rule; the runs differ by `due_on`.
- **Water tasks are anchored at the window's first day.** "Every `every_days`" needs a fixed origin or each daily run would compute different days. The series starts on the first day of the run (1 June, 8 June, … for every 7 days) and only the days from today to today + 90 are inserted, so a missed day is never backfilled.
- **Pending tasks of rules that no longer apply are removed.** After a profile regeneration the rule keys change, and when a plant passes 24 months (or gets a planting date) the stage changes; without a cleanup the old pending tasks would sit on Today for ever. The expansion deletes pending tasks of the plants it processed whose `rule_key` is not among the rules that apply at the plant's age. Done, skipped and snoozed rows are never touched, so the journal keeps its history.
- **`rule_key` months are sorted.** `${type}:${months.join("-")}:${age}` uses the months in ascending order whatever order Claude wrote them, so a regeneration that only reorders the list keeps the same key.
- **Litres in the water task title.** The task row has no litres column, and a watering reminder without the amount is half a reminder, so the expansion writes "Deep summer watering, mature tree (40 L)" as the title. The instruction is the rule's text unchanged.
- **"Today" is the Tunis date on the server.** Vercel runs in UTC; the cron at 05:00 UTC is 06:00 in Tunis, but `src/lib/dates.ts` computes the date in `Africa/Tunis` explicitly so a later schedule change cannot shift it. The app uses the phone's date. Dates travel as `YYYY-MM-DD` strings throughout.
- **Shared date and age helpers.** `src/lib/dates.ts` has no imports and is used by both the app and `api/` (which imports it as `../src/lib/dates.js`, like `src/types.ts`), replacing the two copies of the age calculation in `CalendarSection` and `PlantScreen`.
- **The expansion runs from the app too.** `/api/expand` (bearer token through `verifyUser`) runs the same `runExpansion` as the cron. The Capture screen calls it for the new plant before opening its screen, the Plant screen after a record edit, and Today once per app session plus on Refresh, so tasks never wait for 06:00. The cron remains the daily safety net.
- **`lead_days` waits for Phase 3.** Today lists tasks due within 7 days, which already shows a window a week ahead; the per-rule lead applies to the push digest.
- **Journal text for a skipped task is the reason.** The `journal` view shows `note` in place of the title when the note is set, so a skipped task reads as its reason under the type and status pills; done and snoozed tasks keep their title. Changing the view would need another SQL run, which the pills make unnecessary.

## 2026-10-23 — Phase 1 build

- **Thinking effort on Claude calls.** `claude-sonnet-5-5` thinks adaptively by default and bills thinking as output tokens, which also count against `max_tokens`. The identify call runs at `output_config.effort: "low"` (perception, not planning; keeps the 2,048-token budget for the JSON) and the profile call at `"medium"`. The returned usage includes `thinking_tokens` so the split stays visible. Raise identify to `"medium"` if identification quality disappoints.
- **Function time budget.** `vercel.json` sets `maxDuration: 300` (Fluid compute, the default for new projects, allows it on Hobby). `api/_claude.ts` keeps every call inside `FUNCTION_BUDGET_MS` (280 s): one request timeout equals the time left, the SDK's own retries are off, and the one retry on a transient error or on a cut output (`max_tokens`, doubled as CLAUDE.md asks) only runs when at least 60 s remain. If the Vercel plan rejects 300, lower `maxDuration` and `FUNCTION_BUDGET_MS` together (for example 60 and 55).
- **Bearer check before the method check.** Every route except `daily` answers 401 to any request without a valid token, whatever the method, so acceptance test 5 (open `/api/identify` in the browser) sees 401, not 405.
- **One profile per species, not per cultivar.** The lookup in `api/profile.ts` tries the exact (name, cultivar) pair, then the species-level row, then any row of the species, before calling Claude; otherwise a second photo of the same olive with fruit in frame (identify now returning a cultivar) would write a second profile. The identify output keeps the cultivar in `photos.ai_result`. Scientific names are normalised to the bare binomial (author citation and hybrid sign dropped) before lookup and insert, and both prompts ask for that form.
- **Regeneration resets `confirmed`.** A regenerated profile is new AI text, so the row goes back to "AI-written, confirm"; `user_edits` are re-read after the Claude call so a field saved during the wait is not overwritten, and the review screen disables editing while a regeneration runs.
- **Orphan species rows.** The profile call starts at Confirm, before the plant is saved, so an abandoned capture (Start over, Pick another, leaving the screen) would leave a species nobody uses. The Capture screen deletes a species it created when the capture is abandoned, and the species review screen offers Delete for a profile with zero plants. The foreign key from `plants` is the final guard.
- **Service worker updates prompt instead of reloading.** `registerType: "prompt"` with a "Reload" banner in the layout, because an automatic reload after a deploy would drop a photo mid-capture.
- **Storage policy in the schema.** `supabase/schema.sql` creates the private bucket and the `storage.objects` policy itself, so the SQL editor run is the whole database setup.
- **Refusal fallbacks not enabled.** The Anthropic SDK guidance suggests the server-side `fallbacks` parameter on Sonnet 5.5. CLAUDE.md says to surface a refusal to the user instead, and a fallback would run a model other than the one decided, so the parameter is left out. The identify and profile routes return `{ refusal, ...usage }` with HTTP 200 and the UI shows the text.
- **Prompt files on Vercel.** `api/_claude.ts` reads `prompts/*.md` and `*.schema.json` at runtime through `import.meta.url`, with `process.cwd()/prompts` as fallback, and `vercel.json` lists `prompts/**` in `functions.includeFiles` so the files ship with the functions.
- **`/api/daily` is a stub in Phase 1.** The cron entry in `vercel.json` needs a target, so the route exists and only checks `CRON_SECRET`; task expansion and the digest come in Phase 2.
- **SPA routing.** `vercel.json` rewrites every non-`/api/` path to `index.html` so deep links such as `/plants/<id>` open on the phone.
- **Profile edits are stored per top-level field.** `species.user_edits` keeps whole top-level JSON blocks (`water`, `uses`, …), not individual nested keys. A regeneration keeps those blocks verbatim. Editing `care_calendar` and `pests` by hand is deferred; regenerate instead.
- **i18n entry point.** All strings stay in `src/i18n/en.ts`; `src/i18n/index.ts` only exports the active table as `t`, where Phase 5 will pick `fr`.
- **Profile call timing.** The profile request starts when a candidate is confirmed, before the record form is filled, so the wait overlaps with typing. Save is disabled until the profile is ready.
- **Toolchain pins.** TypeScript stays on 5.9 because typescript-eslint does not support TypeScript 7 yet; Vite 8 and the current React 19 are used.
- **Photos in the journal.** Journal photos (kind `journal`) can be added from the Plant screen already in Phase 1; it costs nothing and fills the journal before tasks arrive.
